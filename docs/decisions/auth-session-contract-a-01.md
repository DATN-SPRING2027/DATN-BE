# A-01 Authentication Session Contract

**Status:** Contract compilation for A-02 and A-03; no new product or security decision.
**Source snapshot:** DATN-BE `56036d1`; DATN-FE `c57c014`.
**Authority:** Workspace [Authentication Decision Closure V1](../../../docs/decisions/AUTHENTICATION-DECISION-CLOSURE-V1.md) §§9.7–12, [Refresh Authentication Decision Closure V1](../../../docs/decisions/REFRESH-AUTHENTICATION-DECISION-CLOSURE-V1.md) §§3–11, and [decision register](../../../docs/decisions/decision-register.md) DEC-010/DEC-016/DEC-017. Earlier proposals in those records are not selected merely because they have example payloads. This file does not amend them.

## Boundary and current state

| Classification | Contract fact |
| --- | --- |
| **DECISION** | Browser authentication crosses the Next.js BFF with HttpOnly cookies. Bearer access is for programmatic/API/service callers; browser code receives no readable access or refresh token. Access JWT lifetime is 15 minutes. |
| **FACT — BE** | Login, `/me`, and Logout exist at `/api/v1/auth/*`; login sets only `continuum_access`. No refresh issuer, refresh route, rotation, or replay handler exists. Logout recognizes a presented `continuum_refresh` cookie but login never issues one. |
| **FACT — FE** | Browser hooks call `/api/backend/auth/{login,me,logout}`; the catch-all BFF forwards these to `/api/v1/auth/*`, forwards `Cookie`, and appends each backend `Set-Cookie` separately. It has no browser refresh flow or public `/api/v1/auth/refresh` handler. |
| **DECISION — refresh** | The sole browser refresh URL is `POST /api/v1/auth/refresh` on the Next.js BFF, forwarded to the NestJS capability at the same path. `/api/auth/refresh` and `/api/backend/auth/refresh` are not alternate refresh contracts. |
| **UNKNOWN** | Browser refresh and multi-cookie delivery on the supported production Node/Next/browser runtime, and refresh transactions on MongoDB 7.0 `rs0`, have not been proven. |

The endpoint rows below distinguish the **implemented WP-04A contract** from the **approved A-02/A-03 refresh target**. A documented target is not a claim that its runtime exists.

## HTTP contract

All bodies shown are JSON. Implemented BE errors use `{ "code": string, "message": string, "details": object, "requestId": string }`; the structured exception filter supplies empty `details` when none is safe to expose. Do not expose credentials or account status in generic authentication failures.

| Endpoint | Request and successful result | Failure behavior and status | State |
| --- | --- | --- | --- |
| `POST /api/v1/auth/login` | `{ "email": string, "password": string, "organizationId"?: string }`; `organizationId` is a selection hint checked against server-side eligible organization context. `200 { "user": { "id", "email", "name", "organizationId", "roles": string[] } }` and `Set-Cookie: continuum_access=...`; no token in JSON. | `401 AUTHENTICATION_FAILED` for invalid credentials, denied user status, MFA-enabled account without an implemented factor, or no eligible context; `409 ORGANIZATION_SELECTION_REQUIRED` with `details.organizations: [{id,name}]` after verified credentials when selection is needed; `422 VALIDATION_FAILED` for malformed fields; current BE can return `429 LOGIN_RATE_LIMITED`. No credential is issued on failure. | Implemented WP-04A. The `429` outcome is current implementation evidence, not a new A-01 policy. |
| `GET /api/v1/auth/me` | Access cookie or `Authorization: Bearer <access JWT>`; `200 { "id", "email", "name", "organizationId", "roles": string[] }`, with no permissions field. A supplied Authorization header takes precedence over the cookie; malformed Authorization does not fall back to it. | `401` for missing, malformed, expired, unverifiable, revoked access token, inactive User, or absent ACTIVE Organization Membership for the token organization. | Implemented WP-04A. Existing `roles` are token claims; refresh of changed role assignments during a live access-token window is not promised. |
| `POST /api/v1/auth/logout` | No JSON request body. `200 { "status": "logged_out" }` even without a valid current credential; clears the known `continuum_access` cookie at `Path=/`. A presented valid access token is revoked for its remaining lifetime by the current security store; a presented `continuum_refresh` cookie is hashed and its matching stored session is revoked if found. | Existing endpoint is idempotent. Storage/transaction failures have no A-01-specific status mapping. No guarantee of cross-device access-token invalidation is made. | Implemented WP-04A. Refresh-cookie clearing at its future Path remains an A-02/A-03 integration obligation; the existing endpoint does not clear it. |
| `POST /api/v1/auth/refresh` | Browser request carries the HttpOnly refresh cookie, a separate readable CSRF cookie, and matching `X-CSRF-Token`. No JSON refresh-token request is selected. On success, atomically consume the old token and persist a new hashed refresh session before issuing replacement access/refresh credentials through cookies. | Missing/malformed/unknown/expired/invalid token: generic `401`, no credentials. Known revoked token: atomically revoke that user's active refresh sessions, then generic `401`, no credentials. Missing/mismatched CSRF: reject without rotating or issuing credentials. Transaction failure: fail closed with no credentials. | Approved MVP behavior; **not implemented**. Exact success HTTP status/body, CSRF failure status/body, transaction-failure status/body, and CSRF cookie name are **UNKNOWN/TBD**. OpenAPI must not imply a JSON token-pair response. |

The login selector/error behavior is the Leader-directed WP-04A implementation disposition in Authentication Decision Closure §10; it does not resolve wider Product/Security authority or the SRS conflicts preserved there. The access cookie currently uses `HttpOnly; SameSite=Strict; Path=/; Max-Age=900`, with `Secure` outside local development/test. It is the only cookie issued by current login. The refreshed MVP browser-cookie target in Refresh Decision Closure §4–5 is `SameSite=Lax`, including authentication and CSRF cookies. This **current-versus-target difference** needs implementation review in A-02/A-03; A-01 does not silently change runtime behavior.

On successful refresh, the target emits **two separate `Set-Cookie` fields**: `continuum_access` at `Path=/`, `HttpOnly`, `SameSite=Lax`, `Max-Age=900`; and host-only `continuum_refresh` at `Path=/api/v1/auth`, `HttpOnly`, `SameSite=Lax`, `Max-Age=604800`. Both are `Secure` in production. The BFF forwards each field independently without comma-joining them. Errors issue no replacement credentials. Whether refresh reissues the separate CSRF cookie is **UNKNOWN/TBD**.

## Session and browser model for A-02/A-03

- **Access credential — DECISION/FACT:** HS256 JWT, `exp = iat + 900`, with current claims `sub`, `email`, `orgId`, and `roles`; browser delivery is the `continuum_access` HttpOnly cookie at `Path=/`. `/me` validates the token, checks current User status and ACTIVE Organization Membership, and consults the current revocation store. DEC-010 permits a short remaining access-token window after refresh-session revocation; a general immediate access-token revocation SLA is **UNKNOWN**. Current Logout's presented-token revocation is implementation evidence, not a user-wide access-token rule.
- **Refresh credential — DELEGATED MVP DECISION:** Opaque cryptographically random value; persist only its SHA-256 hash with user, organization, revoked state, and `expiresAt`. Seven-day lifetime; enforce expiry on use independently of TTL deletion. The browser refresh cookie is host-only (no `Domain`), `HttpOnly`, `SameSite=Lax`, `Secure` in production, `Path=/api/v1/auth`, `Max-Age=604800`; plain-HTTP localhost may omit `Secure`. `continuum_refresh` is the existing BE/SPEC-002 cookie name; the delegated decision fixes its attributes, not a new token acquisition channel.
- **Rotation and replay — DELEGATED MVP DECISION:** One successful use consumes the presented token exactly once and creates its replacement in one transaction. A known revoked token triggers user-wide invalidation of active refresh sessions keyed by persisted `userId`, atomically. No `familyId`, device identity, or new schema field is selected. Missing/unknown credentials cannot identify a user and do not trigger an inferred user-wide revoke. Invalid legacy rows fail closed. Raw refresh values are not persisted or logged.
- **CSRF — DELEGATED MVP DECISION:** Double-submit uses a non-HttpOnly, non-authenticating CSRF cookie at `Path=/` plus matching `X-CSRF-Token` for browser refresh. The value is independent of auth secrets. NestJS compares them; the BFF forwards the Cookie and header without deciding validity. CSRF failure changes no token state. Exact CSRF cookie name and failure status/body are **UNKNOWN/TBD**.
- **BFF — DECISION/FACT:** For the approved browser refresh URL, Next.js owns the browser-facing handler and forwards to NestJS, then relays status, body, and *each* `Set-Cookie` independently, unchanged on success and error. The current `/api/backend/[...path]` proxy has this per-header forwarding code for existing routes; it does not supply the decided refresh URL or browser recovery logic. A-03 must reconcile the route and verify the multi-cookie browser journey. Browser code must not store token values in web storage or receive them in JSON.
- **Programmatic callers — DECISION/DEFERRED:** `/me` consumes Bearer access JWTs. Acquisition and refresh of programmatic Bearer credentials have no approved trusted-caller issuance contract and remain `DEFERRED / CONTRACT_REQUIRED`. Browser login and browser refresh do not become a JSON token endpoint for such callers.

## Handoff and unresolved decisions

**A-02 consumes** the refresh route's NestJS capability, single-use atomic rotation, user-wide known-token replay response, seven-day expiry, hash-only persistence, backend CSRF comparison, and fail-closed behavior. It must not infer a family field or programmatic issuance flow. **A-03 consumes** the sole browser refresh URL, cookie attributes, readable CSRF value/header transport, independent `Set-Cookie` relay, and browser session recovery boundary. Neither task may claim completion solely from this contract.

**UNKNOWN/TBD requiring explicit closure before the corresponding response can be advertised as final:** refresh success status/body; CSRF and transaction-failure status/body; CSRF cookie name; refresh-cookie clearing behavior across Logout and failed refresh; browser recovery trigger/retry policy; programmatic token acquisition/refresh; access-token revocation SLA; G-11 Auth Audit/Outbox policy; production secret provisioning/rotation; MongoDB 7.0 `rs0` transaction/index/legacy-row proof; and browser multi-cookie proof. Do not reuse the draft OpenAPI `AuthSession`/`TokenPair` JSON shape as an approved refresh response.

## 2026-10-05 amendment — A-02 refresh HTTP contract closure

**Decision source:** Explicit A-02 implementation instruction supplied on 2026-10-05. This amendment closes only the refresh-specific HTTP TBDs identified above. Earlier TBD statements remain as the historical A-01 snapshot. Other unresolved A-01 items remain unresolved.

| Boundary | A-02 decision |
| --- | --- |
| Endpoint | `POST /api/v1/auth/refresh` on NestJS, reached through the same public Next.js BFF URL. |
| Success | `200 {"status":"refreshed"}`; `Cache-Control: no-store`; two separate `Set-Cookie` fields for replacement access and refresh credentials. No token value in browser-readable JSON. |
| Invalid refresh | Missing, malformed, unknown, expired, revoked, or replayed credential: generic `401 AUTH_REFRESH_INVALID`, without disclosing the reason. Known revoked replay retains the prior user-wide refresh-session invalidation decision. |
| CSRF | Cookie `__Host-csrf`, header `X-CSRF-Token`; missing or mismatched values: `403 AUTH_CSRF_INVALID` before refresh-session mutation. Cookie is readable by browser JavaScript, `Secure; SameSite=Lax; Path=/`, with no `Domain`. |
| Refresh cookie | `__Secure-refresh`, `Secure; HttpOnly; SameSite=Lax; Path=/api/v1/auth/refresh`, with no `Domain`; seven-day `Max-Age=604800`. This refresh-specific name and path supersede the earlier `continuum_refresh` and `/api/v1/auth` target for A-02. |
| Internal/transaction failure | `500 AUTH_REFRESH_FAILED`, with no replacement credentials, no partial rotation, and no database details in the response. |
| Error representation | Retain the existing scoped structured JSON error architecture (`code`, `message`, `details`, `requestId`). `application/problem+json` is deferred because the current global exception filter does not support it; no global error-format change is authorized here. |

The replacement access cookie remains `continuum_access; Path=/; HttpOnly; SameSite=Lax; Max-Age=900`, with `Secure` in production, and the JWT lifetime remains 15 minutes. Refresh retains the previously approved opaque credential, SHA-256 hash-only persistence, atomic single-use rotation, seven-day application-enforced expiry, and user-wide known-token replay response. This amendment does not choose browser recovery, programmatic acquisition, logout clearing, or a new audit/blacklist policy.

**Research basis, not DATN decision authority:** The [HTTP cookie draft](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis) distinguishes `__Secure-` (requires `Secure`) from `__Host-` (also requires `Path=/` and no `Domain`). The [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) describes cookie-to-header double submit and warns about cookie injection in naive variants; the chosen `__Host-` CSRF cookie constrains host and path but is not a newly selected signed-CSRF scheme. [RFC 9457](https://datatracker.ietf.org/doc/html/rfc9457) defines `application/problem+json`; its adoption here remains deferred as stated above.
